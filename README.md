# ЦДБ — рабочий навигатор

Система Центра доктора Бубновского в Барнауле: трёхслойный маркетинговый план, инструкции, персональные задачи и закрытый HTML-отчёт руководителя.

## Что реализовано

- Персональный вход; роли `director`, `administrator`, `manager`, `contractor`.
- Проверка доступа на сервере. Руководителю доступен импортированный финансовый отчёт; подрядчику — только инструкции его направления.
- Постоянное хранение пользователей и личных задач в SQLite. Задачи не являются CRM и не содержат карточек пациентов. Руководитель не видит личные задачи других сотрудников.
- Три слоя плана: работа с базой, настройка процесса, измеримые рекламные тесты.
- Нет регистрации для посетителей, стандартных паролей и публичной выдачи данных.

Данные не появятся в репозитории после запуска. Каталог `var/` исключён из Git. GitHub Pages не выполняет Python и не подходит для этой версии с закрытыми разделами. Просмотр `index.html` непосредственно на GitHub не запускает систему.

## Запуск на компьютере или сервере

Нужен Python 3.11+. Внешних библиотек нет.

```bash
git clone https://github.com/iamkurakov/centrdb.git
cd centrdb
python3 server.py user director director
python3 server.py user reception administrator
python3 server.py user manager manager
python3 server.py user agency contractor
python3 server.py import-report /absolute/path/bubnovsky-working-report.html
python3 server.py serve --port 8080
```

Для каждого пользователя команда запросит отдельный пароль от 12 символов. Открыть `http://127.0.0.1:8080`. В Windows использовать `py` вместо `python3` при необходимости. Пароли передаются только через скрытый ввод. Повтор команды `user` меняет пароль/роль и завершает прежние сеансы.

Импортировать только доверенный HTML-отчёт. Исходный отчёт находится в материалах проекта; обновлённый рабочий отчёт передаётся отдельно, вне публичного репозитория. Встроенные скрипты отчёта выполняются в изолированном iframe без доступа к родительской странице. Некоторым внешним графикам нужен интернет.

## Рабочее размещение

Понадобится сервер с Python и HTTPS-доменом. Код слушает только localhost; перед ним нужен Caddy или Nginx с TLS. Например, Caddy:

```caddyfile
your-domain.example {
    reverse_proxy 127.0.0.1:8080
}
```

Перед запуском задать реальные значения:

```bash
export CENTRDB_DATA_DIR=/srv/centrdb-data
export CENTRDB_ORIGIN=https://your-domain.example
export CENTRDB_SECURE_COOKIE=1
python3 server.py serve --port 8080
```

Постоянный процесс настроить через systemd или другой менеджер процессов. Запускать от отдельного непривилегированного пользователя, которому доступен только нужный каталог. На прокси ограничить частоту запросов `/api/login`; встроенное ограничение за прокси общее для его адреса. Эта версия рассчитана на небольшую внутреннюю команду, не на публичную высоконагруженную CRM. Входы действуют восемь часов; после истечения нужно войти повторно.

## Хранение и резервные копии

Отдельный репозиторий `data` для работы не требуется: записи сохраняются в `/srv/centrdb-data/centrdb.sqlite3`, отчёт — в `/srv/centrdb-data/report.html`. Они переживают перезапуск и обновление кода при сохранении каталога. При переносе на другой сервер перенести оба файла с закрытыми правами.

Согласованная резервная копия работающей SQLite:

```bash
python3 server.py backup /srv/backups/centrdb-2026-11-01.sqlite3
```

Команда должна запускаться с тем же `CENTRDB_DATA_DIR`. Отчёт копировать отдельно. Перед восстановлением остановить приложение; заменить файл базы резервной копией и запустить снова. Копия содержит хеши паролей и действующие сеансы, поэтому хранить её как закрытые данные.

## Если нужен отдельный репозиторий данных

Доступный в этой сессии GitHub-инструмент не создаёт репозитории. Создать вручную:

1. GitHub → New repository → имя `centrdb-data` (или `data`).
2. Выбрать **Private**, добавить README, нажать Create repository.
3. В Settings → Collaborators дать доступ только владельцу данных и ответственному администратору. Роли приложения не равны ролям GitHub.
4. Хранить там лишь согласованные резервные выгрузки и документы. Рабочая база остаётся на сервере; Git не заменяет базу и не обеспечивает одновременную запись.
5. Не добавлять токен GitHub в браузер или HTML. Не подключать закрытый репозиторий напрямую к GitHub Pages. Файлы с персональными медицинскими данными требуют отдельного решения центра о допустимом месте хранения.

## Ограничения аналитики

Ответов по истории расходов, ФОТ, графикам и условиям курсов не ожидаем. Расчёты строятся на доступных данных с явными допущениями. Полная себестоимость услуг, подтверждённая маржа, прибыль и точка безубыточности пока недоступны как факты. Историческую эффективность отдельных рекламных каналов не восстанавливаем. Код `01465` считаем розничным в пациентской аналитике по рабочему допущению.

Рабочий отчёт сохраняет исторические графики и помечает устаревшие выводы. Он не является полностью пересчитанной финансовой моделью. RFM на 21.10.2026 нельзя использовать для звонков без обновления по текущей 1С. Медицинские рекомендации определяет врач, административные контакты не заменяют консультацию.

## Проверки

```bash
python3 -m unittest discover -s tests -v
```

Проверяются вход, роли, запрет доступа к отчёту, CSRF, изоляция задач и сохранение данных при перезапуске. Проверка браузера и развёртывание на внешнем сервере выполняются отдельно.
